# Performance and pricing notes — 16 October 2026

The Ahrefs slow-page export contains 646 unique, successful, indexable HTML URLs, including 585 testimonial details. It is a selected issue export, not the complete crawl population. Median TTFB is 1,582 ms, p95 4,027 ms; median document loading time is 1,832.5 ms. TTFB accounts for 88.5% of summed document loading time. Ahrefs did not render JavaScript in these rows. Its document timing does not measure image loading, visual completion or Core Web Vitals. The private crawl geography, concurrency, issue threshold and AI-user-agent settings are unknown.

A direct Mac baseline used three rounds across six HTML routes plus robots.txt, with fresh connections and no configured proxy. The 18 HTML responses were all 200 and `private, no-store`, with TTFB 275–1,503 ms (median 408 ms), through Cloudflare MEL. These requests did not reproduce the export's 14.5-second outlier. The first initialization-bearing detail response reported startup and database work; subsequent requests were faster. Server-Timing is captured before Astro finishes streaming, so its query counts and durations do not describe all work in the response. Durations overlap and must not be added.

## Changes and boundaries

- Normalize rich text and extract plain text only when a template accesses that entry's content/body. Reuse the result within its request. Metadata reads no longer process all review bodies. Existing collection query deduplication and independent result arrays remain intact; there is no new per-review query or cross-request content cache.
- Use the supported EmDash image component for review and service cards, passing full CMS media values and layout-specific `sizes`. It retains media/focal-point metadata and generates responsive variants through the existing Cloudflare Images integration. Preserve current responsive detail heroes, native picture posters, deferred video and self-hosted fonts. A representative CMS square image measured 75,506 bytes at 1,000 px and 39,246 bytes at 600 px; responsive selection can reduce transfers, but this does not explain Ahrefs HTML TTFB.
- Update compatible Astro 7.4/Cloudflare adapter 14.4, React integration/React, Markdown tooling, Wrangler and Worker types together. Keep TypeScript 6 because the current Astro checker does not declare TypeScript 7 support. Keep the coordinated EmDash family at 1.1 until current D1/R2 backups and migration review are possible. D1 management returned authentication error 10000 while Worker deployment listing remained available; no credentials were changed.
- Keep public HTML, CMS responses, media, signed previews and authenticated responses private. The current pre-Worker HTML cache cannot safely provide cookie-based bypass under the required contract. KV object caching has eventual invalidation propagation and would weaken the documented immediate-publishing behavior. No cache resource, paid service or security/configuration expansion is provisioned. Shared HTML caching remains deferred until cookie bypass and global publication invalidation can both be demonstrated with the actual editor workflow.

The compatible update reduced npm audit findings from six high/six moderate to zero high/six moderate. Remaining advisories are in the existing typography and archived Markdown-import dependency chains; this is not a statement that all reported packages are reachable by public Worker requests. No forced downgrade or breaking audit fix was applied.

## Pricing contract

The live source is the EmDash `pricing/index` entry, not `src/content/pricing/index.md`. `src/lib/pricing.ts` exposes that entry to the pricing page and `PricingReference.astro`. FAQ, service and celebrant-cost references retain the complete published price string and link to `/serviceandprice`. Existing editorial prose is preserved. CMS publishing remains independent of deployment.

An owner decision is still required for the exact GST and travel terms: the published Australian price says `$2,000 + tax and travel`, the pricing template says `GST included` and allows additional travel fees, while the FAQ says all required booking travel is included. Confirm whether the fee includes GST and which travel is included before reconciling those words. The implementation does not choose a tax policy or change the advertised amounts.

## 17 October 2026 — static-site follow-up and deferred CMS startup

The newer uploaded Ahrefs issue export contains 54 unique slow-page URLs, all HTTP 200 with JavaScript rendering disabled. Median TTFB is 1,241.5 ms, p95 1,774 ms and maximum 2,312 ms. Median document loading time is 1,289.5 ms, p95 2,520 ms and maximum 3,008 ms; 91.08% of summed document loading time is waiting for the first byte. Fifty rows exceed one second TTFB. These are selected issue URLs, so the smaller export does not establish the percentage of the whole site that is slow.

This is fresh post-release evidence. Cloudflare Observability matched the worst URL, `/weddingtestimonials/maddison-and-matthew`, to Ahrefs at 08:18:10.928 Hobart time through IAD (ray `a4ba182d684dc9bf`). Ahrefs measured 2,312 ms TTFB while that Worker invocation recorded 33 ms wall time and 2 ms CPU. A separate Frankfurt probe measured 791 ms TTFB while its matched invocation recorded 13 ms wall time and 1 ms CPU. Those clocks cover different portions of the request; they identify waiting outside the recorded handler execution but do not isolate a Cloudflare internal cause.

A fresh MEL crawl of all 652 canonical URLs returned HTTP 200 with median TTFB 106.5 ms, p95 126 ms and maximum 633.5 ms. Forty-two regional probes reproduced intermittent 500–900 ms waits on public documents, an empty canonical redirect and the same Worker through its workers.dev hostname. Direct Cloudflare trace requests were materially faster. These results make Worker dispatch/startup a useful hypothesis to test; they do not prove the exact cause or imply all visitors experience the same delay.

The local source change keeps `src/worker.ts` limited to public routing and assets, then uses `import()` to load `src/cms-worker.ts` for CMS/private requests and scheduled work. All setup, preview/media authorization, deployment-lock and scheduled publishing logic is retained in that deferred module. There is no new Worker, resource, DNS change or response cache. Public content and images still come from the same committed snapshot.

The emitted eager module graph fell from 1,894,467 bytes across 31 modules to 15,884 bytes across two modules. The CMS is a separate deferred module; the complete uploaded Worker remains approximately 18.4 MiB uncompressed. `scripts/verify-static-build.mjs` now follows emitted static imports and rejects a public startup graph above 32 KiB or a missing deferred CMS chunk. Merely adding source-level `import()` would not be sufficient if a later bundler combined the modules again.

One local Wrangler startup CPU profile recorded 34.6 ms active time for the original entry and 13.9 ms for the deferred entry. Samples are sparse and local hardware differs from Cloudflare; these are diagnostic observations, not a production latency claim. Native workerd checks of the actual new build passed public routing with empty D1, setup protection, admin sign-in redirection, signed draft rendering without analytics, exact-entry token scope, private image transforms and unauthorized-media rejection. No external calls were allowed in those checks. Router regressions also cover CMS initialization failure and cold scheduled delegation.

The initial implementation/testing checkpoint was local, with production still serving `2dd7b4f8505b8efc99ec02bdc1f5fa06388979d3`. Josh subsequently approved deploying the tested change to the existing Worker and repeating the checks. The release evidence below supersedes that earlier pending-approval state. No D1/R2 restore or account/DNS move is part of this change.

### Approved release and regional result — 17 October

Cloudflare build `f3a550fa-79ca-4733-93d6-9d019ad62fc4` passed the full acceptance suite from a fresh checkout of `1b8ec8322e17904fc297bbadc70682d814f98f50`. Its postbuild verified the 15,884-byte startup graph and exact SHA/content hash. The guarded deploy activated Worker `7a649a35-216f-4ad4-b650-84ade0a7b3ef` at 100% traffic at 09:23 Hobart time; both the deployment API and public `release.json` confirm it. Cloudflare reported 9 ms startup time, compared with 28 ms recorded for the previous production build. IndexNow accepted all 652 URLs. Later documentation-only commits may supersede this source/version while retaining the same code and content.

All 652 canonical pages pass live SEO/link checks. A fresh-connection MEL crawl returned all 652 HTTP 200, median TTFB 106.1 ms, p95 123.9 ms and maximum 453.7 ms (previous crawl: 106.5/126/633.5 ms). No response exceeded 500 ms in that local crawl. Public smoke checks pass home, blog, image-bearing review, worst Ahrefs URL, final pagination, pricing, readings, search, RSS, sitemaps, redirects, missing routes, historical original-image SHA256 and CMS sign-in.

The live authenticated editor and publishing status remain healthy. A fresh native signed preview returns 200 with private/no-store/noindex/no-referrer headers, excludes public analytics and loads its protected CMS image with the same private headers. Tampered and wrong-entry tokens return 403; restoring the valid token returns 200. Anonymous media, foreign image transforms, publishing controls and deployment-lock requests remain denied. No CMS content was saved or published during these checks.

The speed issue is **not resolved globally**. Seven post-release measurements reused the exact earlier Globalping probe machines in Ashburn, Frankfurt, London, Singapore, Sydney and New York. Across the five matching canonical public request sets (30 requests, including the empty `www` redirect), median TTFB was 555.5 ms before and 563.5 ms after; 18 versus 17 requests exceeded 500 ms. Maximum changed from 926 ms to 1,100 ms. The repeat review measurement was fast on five probes (39–66 ms) but still took 1,100 ms through IAD. The direct Cloudflare trace control took 20–40 ms after release. This small sample, with varying asset cache state and normal network variation, does not establish an improvement in regional latency or predict a fresh Ahrefs score.

The 1,100 ms IAD result (ray `a4ba78061c59abce`, 09:23:36.445 Hobart) matched the new Worker version with 20 ms wall time and 1 ms CPU. The 718 ms IAD `www` redirect (ray `a4ba77b25c1ec9b4`) matched the same version with 0 ms wall time and 0 ms CPU. The empty redirect does not touch CMS, D1 or static assets. These are different timing scopes, so do not treat their difference as an exact internal duration. Waiting outside recorded handler execution remains the investigation target; full-bundle loading, dispatch and other Cloudflare request processing have not been individually isolated. The reduced startup dependency graph is verified, but it is not a sufficient fix for the remaining regional delay. Keep the healthy existing-account deployment and its publishing workflow available while investigating; do not loosen preview security or change resources/DNS on the strength of this hypothesis.
