# Public delivery and CMS releases

Josh requested completion of the production delivery work on 17 October 2026, authorizing the necessary existing-account service connection and traffic switch after testing. The Jake-owned Cloudflare account migration remains deferred. This document describes the implementation; dated live deployment evidence belongs in project history and the current handoff.

## Resources and boundaries

`marriedbyjake-public` is the small public Worker described by `wrangler.public.jsonc`. It serves the exact committed Astro output, including historical/canonical redirects and testimonial query pagination. Its only bindings are ASSETS and the HTTP service binding CMS → `marriedbyjake`. Public requests never load Astro/EmDash or access D1, R2, sessions, Images or publishing credentials. The complete script is limited to 32 KiB, with a strict dependency allowlist. Production JavaScript, Maps, videos and forms retain their existing behavior.

The existing `marriedbyjake` Worker retains EmDash, all private resources and secrets, the sole maintenance/publishing cron and its public fallback assets. Original private Requests are forwarded through the service binding, preserving their canonical URL, Origin, cookies, body and signed-preview token. Responses stream back with their authentication/privacy headers and Set-Cookie unchanged. Private operations on the public workers.dev hostname are denied instead of adding that hostname as a trusted passkey/CSRF origin. Its public diagnostic pages are noindex and its robots.txt disallows crawling. A CMS transport failure returns a private 503 for the editor while committed public pages remain available.

Canonical and www route ownership is declared in `wrangler.public.jsonc`; the backend configuration declares no public routes. Route activation is a separate reviewed operation, never part of ordinary version releases. Existing routes remain intact while the isolated public endpoint is prepared and tested. Both Workers retain workers.dev access for release checks; that address is not an isolated CMS staging database.

## Hosted build sequence

Both Workers connect only to `marriedbyjake/marriedbyjake`, `main`, with preview builds disabled. Each Cloudflare Builds job uses its own Cloudflare-provided Worker identity and the same reviewed repository SHA. Never override CI identity/tag/name variables to deploy a different Worker from a job.

| Target | Build command | Deploy command |
| --- | --- | --- |
| Existing CMS Worker | `npm ci && npm run validate` | `npm run deploy:ci` |
| Public Worker | `npm ci && npm run validate` | `npm run deploy:public:ci` |

Use Node 24.21.0, existing restricted Maps build configuration, account ID and the approved interim dedicated Cloudflare Builds credential. Both jobs need `PUBLISHING_DEPLOY_APPROVED=true` and the same masked deployment-lock `PUBLISHING_BUILD_SECRET`. That secret operates only the deployment lease, never CMS content, media or Cloudflare APIs. The publisher App key and encryption key remain only in the CMS runtime and private recovery storage. The public Worker has no runtime secret. Account ownership changes remain separate from this delivery release.

`npm run validate` includes content and publisher tests, binding generation, Astro diagnostics, complete static output checks, packaging and native public-service checks. The generated public package is `.emdash/public-delivery/`, with a separate `server/worker.mjs` and explicit ASSETS path. No additional module discovery, private environment file or server build is attached to the public upload. Generated public/backend binding declarations are ignored and regenerated by `npm run types`.

Both deployment commands verify exact clean main/CI source, content/image checksums and package identity. The public job waits up to 15 minutes for the backend workers.dev release to match both source SHA and content hash, before claiming any lock. Both jobs claim/renew the existing private D1 deployment lease through the dedicated endpoint on the backend; a busy lock retries briefly without changing traffic. Stale source and unauthorized requests fail closed.

Wrangler `versions upload --keep-vars` uploads an inactive version. An exact structured receipt identifies the intended Worker and version. Source is checked again after upload. `versions deploy <exact-version>@100 --yes` activates it without mutating routes or cron. The prior single active version is recorded before upload; active traffic and live release/smoke checks follow activation. Failed or uncertain activation/live checks restore that recorded prior version while the lease is still owned and verify its traffic. Losing lease authority fails closed rather than overwriting a potentially newer deployment.

The backend upload omits `PUBLISHING_ENABLED` from its generated variables, preserving the owner-controlled true/paused setting and existing secrets. The public job rechecks the matching backend after acquiring the shared lock. Its source/hash and public checks must pass before the job succeeds. IndexNow runs only after successful public deployment. The publisher confirms only the exact source SHA and content hash served on the canonical domain, so a successful backend deployment alone cannot falsely confirm a public content release.

## Cutover and recovery

Before initial traffic switch, preserve the current route IDs/targets, both active version IDs, Git head/source/hash, current CMS export and existing SQL/media recovery files privately. Verify all canonical documents, image bytes, redirects, query pagination and actual CMS setup/auth/preview/media behavior through the service path. Test desktop/mobile public JavaScript, Maps/video/form rendering, authenticated editor/publisher state and signed-preview privacy. Never create or publish disposable production content for this release.

Bootstrap the public Worker only with its generated configuration, whose `routes` is empty. Once the exact isolated release and hosted build configuration pass, reassign the existing canonical/www route IDs to `marriedbyjake-public`; no DNS/account/record change is required. Verify canonical source/hash, active traffic, all pages, CMS/session/private previews and regional results. Keep the existing Worker and its fallback assets available.

For code/assets rollback, pause automatic Builds and runtime publishing, retain newer CMS data, then restore the recorded healthy public version and verify it. If public routing/service connectivity is the problem, reassign the same two route IDs to `marriedbyjake`, verify the backend fallback release and private behavior, then reconcile Git/CMS/public state before resuming. Version-based builds do not steal routes back from the chosen rollback target. A rollback never restores an older D1 database or media archive over new drafts/revisions. Retain both healthy version IDs and private recovery material.
